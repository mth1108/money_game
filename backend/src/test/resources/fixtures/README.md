## 왜 저장소에 두는가

- 통합 테스트가 실제 API 를 부르면 느리고, **허용 IP 가 등록되지 않은 환경에선 실패**합니다
  (토스 API 는 IP 화이트리스트 방식입니다)
- 밸런스 조정은 같은 구간을 반복해 돌려야 비교가 됩니다
- 전체 원본은 `data/` 에 두고 `.gitignore` 대상입니다. 여기에는 성격이 다른 구간만 골라 넣습니다

## 형식

- `CsvCandleWriter` 출력과 같습니다. 헤더 `timestamp,open,high,low,close,volume`, 시간 오름차순, LF
- 파일 하나 = 연속한 **241봉** = 시작가 1봉 + 240틱 (CLAUDE.md §3 M4 「시세와 틱의 관계」).
  `data/samples/<symbol>_<interval>.csv` 의 연속 구간을 그대로 잘랐습니다
  - 2026-10-02 에 240봉에서 241봉으로 늘렸습니다. 시작 봉은 그대로 두고 바로 다음 봉 하나를 뒤에 붙였습니다
  - 원래 240봉이 샘플과 정확히 일치하는지 확인한 뒤 붙였습니다
- `timestamp` 의미 (CLAUDE.md §3 M1)
  - `1m` — 봉 종료 시각. 구간은 `[timestamp − 1분, timestamp)`
  - `1d` — 거래일 (KST 자정)

## 분봉은 `09:01 ~ 15:20` 안에서만 자른다

| 봉 | 실제 구간 | 거래량 0 비율 |
|---|---|---|
| `09:00` | `[08:59, 09:00)` — 개장 전 | 100% (14일 전부) |
| `15:21` ~ `15:30` | 종가 단일가. 연속 체결 없음 | 100% (14일 전부) |

- 이 둘을 빼면 거래량 0 봉이 2.8% → 0.3%, 최대 연속 11봉 → 1봉으로 떨어집니다
- 날짜를 넘기지 않습니다. 오버나이트 갭이 섞이면 압축 재생이 어색해집니다
- 위 분봉 픽스처 3개는 모두 이 조건을 지키며, 거래량 0 봉이 하나도 없습니다

## 시나리오 적격성 기준 (M3)

```
MAX_ZERO_VOLUME_RATIO     = 0.05
MAX_CONSECUTIVE_ZERO_BARS = 5
MIN_SWING_1M              = 0.025
MIN_SWING_1D              = 0.30
```

- 연속 검사는 비율 검사와 별도로 필요합니다. 240봉 중 12봉이 흩어진 경우와 연속으로 멈춘
  경우를 비율만으로는 구분하지 못합니다. 1틱 = 1초라 후자는 12초간 화면이 멈춘 것으로 보입니다
- 값은 확정이 아닙니다. 근거와 조정 방침은 CLAUDE.md §3 M3 · §8 에 있습니다
